# KGHeartbeat Assessment Service

Assess the quality of a Knowledge Graph from a SPARQL endpoint, an RDF dump URL,
or an uploaded RDF file. The service powers the web app's **Assess a KG** page
and provides an HTTP API for submitting assessments and downloading results.

Each assessment produces CSV and Turtle files. A private link lets you follow
its progress and retrieve the results later, including after closing the browser.

The service runs a FastAPI application and a background worker. Job state and
results are stored in SQLite on a shared local filesystem. It accepts one
assessment at a time and does not require MongoDB. The web app's MongoDB catalogue
is managed separately; these assessments are not automatically added to it.

## Quick start with Docker

From the repository root, start the API and worker:

```bash
docker compose --profile webapp up -d --build assessment-api assessment-worker
```

The API is available at <http://localhost:8000>, with interactive documentation
at <http://localhost:8000/docs>. Job data persists in the `assessment-data` volume.

To include the web interface and its catalogue services:

```bash
docker compose --profile webapp up -d --build mongodb backend frontend assessment-api assessment-worker
```

Open <http://localhost:3001/pages/Assess> to submit an assessment. These commands
start the selected services without launching a batch analysis. See the
[container guide](../docker/README.md) for batch runs, catalogue imports and
Docker configuration.

## Run locally

Use Linux and Python 3.11. From the repository root, create a virtual environment
and install the service and assessment engine dependencies:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r docker/requirements.txt -r assessment_service/requirements.txt
python -m nltk.downloader punkt punkt_tab
cp assessment_service/.env-example assessment_service/.env
```

The runtime requirements in `docker/requirements.txt` are shared with the
container image. Installing native Python dependencies may require a C/C++
compiler and Python development headers.

Start the API:

```bash
python -m uvicorn assessment_service.api:create_app --factory \
  --host 127.0.0.1 --port 8000 --no-proxy-headers --no-access-log
```

In another terminal, activate the same virtual environment and start the worker
from the repository root:

```bash
source .venv/bin/activate
python -m assessment_service.worker
```

Both processes load `assessment_service/.env`. They must use the same
`KGH_STATE_DIR` so the worker can find submitted jobs. To connect a locally running
frontend, follow the [web app setup guide](../KGHeartbeat-WebApp/README.md).

## Using the API

### Submit a SPARQL endpoint or RDF URL

```bash
curl http://localhost:8000/assessments \
  -H 'Content-Type: application/json' \
  -d '{"type":"sparql","url":"https://example.org/sparql","output_format":"csv"}'
```

For a downloadable RDF dataset, use `"type":"rdf_dump"` and its download URL.
`output_format` accepts `csv` or `ttl` and defaults to `csv`.

A successful submission returns `202 Accepted` with an assessment ID, its status,
and the URLs used to track and download it:

```json
{
  "id": "<token>",
  "status": "queued",
  "output_format": "csv",
  "status_url": "http://localhost:8000/assessments/<token>",
  "result_url": "http://localhost:8000/assessments/<token>/result",
  "created_at": "2026-09-21T12:00:00+00:00",
  "started_at": null,
  "finished_at": null,
  "error": null
}
```

Save the returned link. Anyone with it can access the assessment; no account is
required, and there is no public listing of assessments.

URL submissions optionally accept an `Idempotency-Key` header. Use a new UUID
for each assessment and reuse it when retrying a request whose response was lost.
Retries with the same key, input and client IP return the original assessment.
File uploads do not support this header.

### Upload an RDF file

Send the file as the request body:

```bash
curl 'http://localhost:8000/assessments/upload?filename=dataset.ttl&output_format=csv' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @dataset.ttl
```

Supported extensions are `.ttl`, `.rdf`, `.xml`, `.nt`, `.nq`, `.trig`, `.n3`,
`.jsonld` and `.json`. Files may be compressed with gzip, bzip2 or xz, or supplied
in a ZIP archive containing RDF files. Uploads must finish within five minutes.
Temporary input files are removed after processing.

### Check progress and download results

```bash
curl 'http://localhost:8000/assessments/<token>'
curl -OJ 'http://localhost:8000/assessments/<token>/result?format=csv'
```

Poll the status URL every five seconds until the status is `completed`, `failed`
or `timed_out`. Once completed, download either format with `?format=csv` or
`?format=ttl`. Both are generated by the same assessment, so changing format does
not rerun it. Files are named `YYYY-MM-DD.csv` and `YYYY-MM-DD.ttl`.

CSV results can be opened in the web app's **Upload your analysis** page. Turtle
results represent the assessment using the Data Quality Vocabulary (DQV).
A completed assessment may still contain unavailable metrics if the source could
not be queried. The CSV `Extra_Triple-retrieval` column describes triple sampling
and coverage.

URL assessments also request a KGSum profile, saved in the private job directory.
Profiles are not included in the CSV or Turtle downloads. Uploaded RDF files
are not sent to KGSum.

### Common responses

| HTTP status | Error | Meaning |
|---|---|---|
| `409` | `assessment_busy` | Another assessment is uploading, waiting for the worker or running. Try again later. |
| `409` | `result_not_available` | The assessment has not completed successfully. Check its status. |
| `409` | `idempotency_conflict` | The submission key was already used with different input. |
| `429` | `ip_limit_exceeded` | The submission quota was reached. Check the `Retry-After` header. |
| `404` | — | The assessment link is invalid or unknown. |
| `413` | — | The request exceeds the configured size limit. |
| `422` | — | The input or requested format is invalid. |

## Configuration

For local runs, edit `assessment_service/.env`. Process environment variables
take precedence. For Docker, set variables in the Compose service environment;
local `.env` files are not copied into the image. Restart the affected services
after changing settings.

| Variable | Default | Description |
|---|---|---|
| `KGH_STATE_DIR` | `var/assessments` | Persistent job storage. Relative paths resolve from the repository root. |
| `KGH_PUBLIC_URL` | `http://localhost:8000` | Public API URL used in returned links. May include a proxy path prefix. |
| `KGH_CORS_ORIGINS` | Empty | Comma-separated frontend origins allowed to access the API. |
| `KGH_SUBMISSIONS_PER_DAY` | `3` | Accepted submissions per IP over a rolling 24-hour period. |
| `KGH_TIMEOUT_SECONDS` | `3600` | Assessment timeout and per-process CPU time limit, in seconds. |
| `KGH_MAX_DUMP_BYTES` | `1073741824` (1 GiB) | Maximum upload, download and expanded RDF size. |
| `KGH_MEMORY_BYTES` | `4294967296` (4 GiB) | Virtual memory limit per assessment process. |
| `KGH_DISK_BYTES` | `2147483648` (2 GiB) | Per-job disk watchdog threshold and per-file size limit. |
| `KGH_TRIPLE_LIMIT` | `1000000` | Maximum triple preview size. |

The supplied local environment example uses `assessment_service/data` for
storage. Compose uses `/app/var/assessments`, backed by a named volume.

Accepted submissions count toward the quota even if they fail. Busy responses
do not. Clients sharing an IP address share a quota; IPv6 addresses within one
/64 are grouped together.

## Deployment

Deploy the API and one worker on a single Linux host with persistent local
storage. Use the supplied Compose services or a process manager to keep them
running. Back up the state directory and set a retention policy: saved results
and logs do not expire automatically.

For a public installation:

- Put the API behind an HTTPS reverse proxy and set `KGH_PUBLIC_URL` and
  `KGH_CORS_ORIGINS` to the public API and frontend addresses.
- Configure proxy request size, timeout and rate limits. Keep private assessment
  URLs out of access logs and analytics.
- When forwarding client IPs, replace `--no-proxy-headers` with
  `--proxy-headers --forwarded-allow-ips=PROXY_IP`, using the actual trusted proxy
  address. Accurate client IPs are needed for submission quotas.
- Run the worker with a dedicated service account, restricted outbound network
  access and container or service resource limits. Per-process memory limits and
  the disk watchdog do not replace aggregate resource limits.

The service rejects private-network URL destinations and local file paths.
Workers should still have outbound firewall restrictions, since native
libraries may bypass Python's network checks.

An API restart leaves the independent worker running. Waiting jobs remain in
storage. After a worker interruption, an unfinished running job is marked failed
when the worker recovers; it is not automatically retried. Keep one worker
instance per deployment and do not remove lock files to force a restart.

For a job that remains queued, confirm that the worker is running and uses the
same state directory as the API. For a failed job, inspect `worker.log` in that
job's directory under `KGH_STATE_DIR`.
